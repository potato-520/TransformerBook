4.3 KV Cache 机制与显存加速 (KV Cache & Memory Scaling)

本节目标：深入剖析大模型推理中的“第一核心性能生命线”——KV Cache，理解 Prefill（首字填充）与 Decode（自回归解码）两个截然不同的计算阶段，掌握显存容量精确计算公式。

1. 它解决什么问题？ (工程师视角黑盒引入)

在自回归文本生成中，当生成第 $t$ 个词时： $$x_1, x_2, \dots, x_{t-1} \longrightarrow \text{模型} \longrightarrow x_t$$ 由于因果掩码的存在，历史 Token 的 Key 和 Value 向量是完全固定、永远不会发生改变的！
如果不做缓存，每生成 1 个新词，都要将过去所有 Token 的 QKV 重新投影一次（复杂度 $O(L^2)$）。
KV Cache 机制：把已经计算过的历史 Key 和 Value 直接持久化缓存在显存中！每生成 1 个新词，只需计算这 1 个新词的 Query，并与缓存好的历史 KV 做点积（复杂度降为 $O(L)$）！

2. Prefill 阶段 vs Decode 阶段

对比维度 Prefill 阶段 (首字处理 / 提示词编码) Decode 阶段 (自回归逐字生成)
输入张量长度 全部 Prompt：$L = L_{prompt}$ 单个最新 Token：$L = 1$
计算特征 Compute-bound（算力受限），大型 GEMM Memory-bound（显存带宽受限），GEMV
KV Cache 操作 一次性计算全部 Prompt 的 KV 并写入 Cache 读取全部历史 KV，计算后追加写入 1 个新 KV

4. 工业级 KV Cache 显存容量精确计算公式

显存占用公式（以字节为单位）：
$$\text{KV Cache Size} = 2 \times (\text{Key} + \text{Value}) \times \text{Layers} \times \text{Heads}_{kv} \times d_k \times \text{SeqLen} \times \text{BytesPerElem} \times \text{BatchSize}$$
实战案例（LLaMA-3 8B, 32 层, 8 个 KV 头, $d_k=128$, FP16 每元素 2 字节）：
单个 Token 产生的 KV 缓存显存开销： $$2 \times 32 \times 8 \times 128 \times 2 \text{ Bytes} = 131,072 \text{ Bytes} \approx 0.125 \text{ MB / Token}$$ 当并发请求 $Batch=16$，上下文长度 $SeqLen=8192$ 时： $$\text{总 KV 缓存} = 16 \times 8192 \times 0.125 \text{ MB} \approx \mathbf{16.38\text{ GB!}}$$ 惊人事实：仅仅存放中间 KV 缓存所占用的显存，就已经超过了 8B 模型权重本身的显存占用（约 15GB）！

5. 打开黑盒：真实工程细节 (PagedAttention 与 vLLM 革命)

操作系统的分页虚拟内存启示：
在传统的 PyTorch 实现中，必须为每个请求提前连续预分配最大长度（如 8k）的显存，导致大量内部碎片（高达 60%~80% 显存被白白浪费）。
vLLM 开创的 PagedAttention 借鉴了 Linux 操作系统的虚拟内存分页机制：将 KV Cache 切分为固定大小的内存页（Page，如 16 个 Token 一页），按需动态分配不连续物理显存，将显存浪费率从 70% 骤降到 4% 以下，直接让大模型服务并发吞吐量飙升了整整 4 倍！
